# 量纲关系浏览器（Dimensional Relation Browser）设计文档

日期：2026-05-26
版本：v2（依据"展示优先依据现实物理式子，含乘除/求导/积分/矩阵"的要求重写）
状态：待评审

## 1. 问题与定位

### 1.1 这不是量纲计算器

本工具的定位是**教学演示用的量纲关系浏览器**，不是数值计算器。它不关心"72 km/h 等于多少 m/s"，而关心：

> 给一个单位或物理量的名称，把它在 SI 下的量纲结构、同量纲的各种单位写法、以及**产生这些量纲关系的现实物理式子**，完整地摊开给人看。

### 1.2 目标体验

1. 输入一个单位/物理量名称（牛、力矩、弯矩、电场强度……）
2. 显示它的英文符号
3. 显示它在 SI 下的量纲
4. 按量纲组合分支成各种其他单位组合（`A = abc = Bc = aC`）
5. **每一步都保持中文名称显示**
6. 在下方展示使用了这种量纲变换的真实物理式子

### 1.3 v2 的核心修正

v1 把"关系从哪来"交给两套机制：预置分解表（默认）+ 向量格搜索（展开更多）。v2 确立更根本的原则：

> **量纲之间的关系优先由现实物理式子给出。代数规则（乘除、求导、积分、矩阵）只是解析这些式子、推导量纲的运算规则。**

这条原则带来三个结构性后果（见第 2 节）：

1. 量纲关系分为**两类本质不同的边**，必须分开建模和展示
2. **代数规则表**成为一等核心组件（求导/积分/矩阵的量纲变换规则）
3. **公式库**从"条目附属字段"提升为**一等公民**，树的边主要来自它

### 1.4 成功判据

- 输入"牛"，能看到 `N → kg·m·s⁻² → J/m, W·s/m, Pa·m² …` 分支树，每层带中文名，**每条边标注来源物理式子**
- 输入"电场强度"，能看到 `N/C`、`V/m`、`kg·m·s⁻³·A⁻¹` 三种同量纲写法，以及 `E = F/q`、`E = U/d`、`E = -∇φ`
- 输入"力矩"与输入"能量"，工具能指出量纲相同但物理意义不同
- 输入"转动惯量"，能展示它是 3×3 张量、元素量纲 `[M·L²]`，并给出 `I = ∫∫∫ r²ρ dV`
- 代数规则（尤其行列式、二重积分）有独立单元测试
- 引擎可通过自动化测试验证，不依赖人工逐条目测

## 2. 核心设计决策

### 2.1 量纲向量是唯一的键，不是单位名

维度向量（如 `{M:1, L:1, T:-2}`）作为索引主键。理由：

- 输入"牛"、"牛顿"、"N"、"force" 都能落到同一入口（别名归一化）
- `牛·米` 与 `焦耳` 自动落到同一个键上，这正是"分支"效果的来源
- 无需为单位名之间的等价关系维护特例代码

### 2.2 两类边必须分开：等价重写 vs 泛函生成

这是 v2 最重要的认知修正。现实物理式子给出的量纲关系分两种**本质不同**的类型：

**类型 ① 同量纲等价重写（`equivalence`）**
`N` = `kg·m·s⁻²` = `J/m` = `W·s/m` = `Pa·m²`
→ 量纲向量**不变**，来自代数恒等变换（乘除、代入消元）。
物理意义：**同一个量，换一种写法**。

**类型 ② 泛函生成的新关系（`derivative` / `integral` / `matrix`）**
`N` = `dJ/dx`（功对位移求导得力）
`[M·L·T⁻¹]` = `∫[M·L·T⁻²]dt`（力对时间积分得动量）
`[M·L²]` = `∫∫∫ρr²dV`（密度对体积加权得转动惯量）
→ 量纲向量**由被作用量除以/乘以变量的量纲得到**。
物理意义：**一个新的函数量被定义出来**，不是同一个量。

**混在一起展示会让学生彻底糊涂**：`J/m` 和 `dJ/dx` 都指向力的量纲，但前者是"力的另一种写法"，后者是"功沿位移的变化率恰好具有力的量纲"——这是完全不同的话。

因此：**每条边必须携带 `kind` 标记**，界面用不同视觉样式区分，并给出口语化解释。

### 2.3 代数规则表：一等核心组件

求导、积分、矩阵的量纲变换**必须显式建模**，否则会算错。

| 运算 | 量纲变换 | 依据 |
|---|---|---|
| `∂f/∂x` | `dim(f) − dim(x)` | 导数定义（差商极限） |
| `∫f dx` | `dim(f) + dim(x)` | 积分是和的极限，量纲线性 |
| `∫∫f dA` | `dim(f) + 2·dim(x)` | 逐重累加 |
| `∫∫∫f dV` | `dim(f) + 3·dim(x)` | 逐重累加 |
| `tr(A)` | `dim(A)` 不变 | 对角元之和 |
| `det(A)` | `n · dim(A)`（n×n） | 定义含 n 重乘积 |
| `A·x`（矩阵乘向量） | `dim(A) + dim(x)` | 逐项乘积求和 |
| `A·B`（矩阵乘矩阵） | `dim(A) + dim(B)` | 逐项乘积求和 |
| `∇f` | `dim(f) − dim(x)` | 各分量偏导 |
| `∇·F`（散度） | `dim(F) − dim(x)` | 分量偏导求和 |
| `∇×F`（旋度） | `dim(F) − dim(x)` | 分量偏导 |
| `1/ρ`（曲率） | `−dim(ρ)` | 纯代数 |

**行列式那条最容易错**：2×2 矩阵每项为 `[L]` 时 `det` 得 `[L]²`，不是 `[L]`。必须写测试固化。

### 2.4 矩阵：元素有量纲，结构无量纲

`I = ∫∫∫ ρ r² dV` 中，**转动惯量是 3×3 惯性张量，但每个元素都是 `[M·L²]`**。

建模原则：

> **矩阵元素有量纲；矩阵结构（行数、列数、对称性）本身无量纲。**

- `kg·m²` 的矩阵与 `kg·m²` 的标量在**量纲层面等价**，但在**结构层面不同**
- 因此条目需要可选字段 `structure`（`scalar` / `vector` / `matrix` / `tensor`），它**不参与量纲运算**，只用于展示与代数规则选择
- 选错代数规则会算错（对标量用 `det` 无意义），所以 `structure` 是规则分发依据

### 2.5 量纲形状模式：公式库的组织方式（设计机会）

`J = -D∇c`（菲克定律）和 `F = -k∇x`（类似形式）在**量纲分析层面形状完全相同**——都是"某量的梯度"。

因此公式库不必逐条硬编码量纲推导，而可归纳为**量纲形状模式**：

```
模式"梯度型"：  dim(结果) = dim(势) − dim(坐标)
  实例：E = -∇φ,  F = -k∇x,  J = -D∇c,  g = -∇Φ
```

好处：

- 一条模式覆盖多条公式，减少数据维护量
- 模式本身是教学概念（"梯度降低一阶量纲"），可以直接展示给学生
- 新增公式时先匹配模式，匹配不上才写显式规则

### 2.6 树的边主要来自公式库，而非算法枚举

v1 最担心"枚举噪声"。确立 1.3 的原则后，此问题大幅缓解：

> 边的来源优先级：**公式库反查（一等）→ 预置分解表（二等）→ 有界搜索（三等，标注为算法生成）**

`J/m` 之所以出现在"牛"的子树里，是因为存在真实物理式子用到它，而非因为数学上相等。展示关系从"算法生成"变为"公式库引用"，**质量与数量同时受控**，且每条边都能标注来源。

### 2.7 算法生成的结果必须标注

"展开更多"的搜索结果来自算法枚举，**不是**来自现实公式。必须在视觉上明确区分：

- 公式库来源 → 正常显示，附公式引用
- 算法搜索来源 → 灰色/虚线段，标注"算法生成，非具体物理式子"

这是教学诚实性要求。不标注会让学生误以为这些组合有物理来源。

### 2.8 同量纲异构必须分开展示

`{M:L²T⁻²}` 同时对应**力矩**（N·m）和**能量**（J）。设计上：

- 同一维度键下挂多个物理量条目，**并列成多棵子树**，不合并
- 显式提示"量纲相同，物理意义不同"——这个提示本身就是教学价值点

### 2.9 弧度：设计被实现推翻（重要变更）

**v2 原设计**：用 `RAD` 伪维度参与运算，让力矩 `N·m` 与能量 `J` 在量纲上分开。

**实现结论：该方案不可行，已放弃。** 原因是代数事实：

```
若 dim(θ) = {RAD: 1}，要使 W = M·θ 成立，需 dim(M) = {RAD: -1}
但向量空间里 rad·rad = {RAD: 2}，不是 0
「弧度相乘相消」是模 2 运算（XOR），与量纲的加减代数不兼容
```

「仅在 M·θ 时相消」也不行——那是特例，不是代数。

**改为**：弧度不进量纲（如实反映 rad 无因次）。后果是物理事实的直接呈现：

```
dim(力矩)   == dim(能量) == dim(弯矩) == M·L²·T⁻²
dim(角速度) == dim(频率)             == T⁻¹
```

**这不是缺陷，而是量纲分析的核心一课**：量纲相同不足以判定物理量相同。
工具改用 `homogeneous_with` 字段 + 公式库上下文（r×F 还是 F·s）来区分，
并在界面上以「⚠ 同量纲异构」显式警示。这比用假维度掩盖更诚实、更有教学价值。

### 2.10 变量名的歧义必须显式建模

公式里求导/积分变量常写成 `x`、`t`、`V`，但单字母变量与单位符号高度重名：
`s` 既是「秒」又是时间变量，`m` 既是「米」又是质量，`T` 既是「特斯拉」又是温度。

处理方式：

- 新增 `variable_units.json` 把变量名映射到惯用单位
- **该映射的解析优先级高于单位符号表**——因为在 `wrt`（对谁求导）位置
  它一定是变量语义，不可能是单位
- 空间求导变量统一写 `x`（不用 `m`，因为后者必然歧义），体积积分写 `V_vol`

若让单位表优先，`p = ∫F dt` 的积分变量会被解析成路程（长度），
导致整条泛函分支静默消失——这是实现中真实踩过的坑。

## 3. 数据模型

### 3.1 一层半结构

```
量纲向量（键）    {M:1, L:2, T:-2}
    ├─ 物理量条目  中文名 / 英文符号 / 类别 / 别名 / structure / 公式实例
    ├─ 单位条目    中文名 / 符号 / 别名 / 换算因子 / 偏移量 / 制式
    └─ 公式条目    表达式 / 符号量纲签名 / 运算类型 / 中文说明
+ 代数规则表（运算 → 量纲变换）
+ 量纲形状模式表（模式 → 变换规则）
```

### 3.2 单位条目 `units.json`

```json
{
  "kind": "unit",
  "id": "N",
  "zh": "牛",
  "symbol": "N",
  "aliases": ["牛顿", "newton"],
  "dim": {"M": 1, "L": 1, "T": -2},
  "factor": 1.0,
  "offset": 0.0,
  "prefixable": true,
  "system": "si-derived"
}
```

- `factor`：相对 SI 基准的换算因子（仅乘除换算用）
- `offset`：**仅温标使用**（°C 为 273.15），默认 0
- 词头（k/M/m/μ）**不进注册表**，作为可组合前缀单独处理
- `system`：`si-base` / `si-derived` / `accepted` / `mixed`

### 3.3 物理量条目 `quantities.json`

```json
{
  "kind": "quantity",
  "id": "moment_of_inertia",
  "zh": "转动惯量",
  "symbol": "I",
  "dim": {"M": 1, "L": 2},
  "structure": "matrix",
  "category": "力学",
  "unit_forms": ["kg·m²"],
  "decompositions": [
    {"expr": "kg·m²", "zh": "千克二次方米"}
  ]
}
```

`structure` 取值：`scalar` / `vector` / `matrix` / `tensor`。**不参与量纲运算**，仅用于展示与代数规则分发。

### 3.7 数据自检（启动时强制执行）

`dim` 是手写的，笔误必然发生。启动自检必须覆盖：

1. 每条 `unit_forms` 表达式求得的量纲 == 条目 `dim`
2. 每条 `decompositions` 表达式求得的量纲 == 条目 `dim`
3. **每条 `formulas` 的 `signature` 按 `ops` 推导的量纲，lhs 与 rhs 必须相等**（公式库自身的齐次性检查）
4. `relations` 引用的单位/量 id 必须存在
5. `algebra_rules` 的 `op` 必须被求值器实现

**任一不符 → 引擎启动即报错，指明具体条目与字段。** 这一步把"手写数据"的风险从"界面上的隐蔽错误"提前到"加载时显式失败"，是数据可持续维护的前提。

## 4. 引擎设计（Python）

### 4.1 模块划分

| 模块 | 职责 | 依赖 |
|---|---|---|
| `dim.py` | 量纲向量类型：加减、取负、缩放、相等、序列化 | 无 |
| `registry.py` | 加载全部 JSON、别名归一、启动自检、按键索引 | `dim` |
| `parser.py` | 单位表达式 → AST | 无 |
| `evaluator.py` | AST → (系数, 量纲向量, 中文写法) | `dim`, `registry` |
| `algebra.py` | 代数规则表执行：求导/积分/矩阵/梯度 | `dim` |
| `formula.py` | 公式条目消解、模式匹配、关系抽取 | `dim`, `algebra` |
| `tree.py` | 建树：**公式库优先** → 分解表 → 搜索 | `registry`, `evaluator`, `formula` |
| `search.py` | 向量格 BFS，分批返回，标注为算法生成 | `dim`, `registry` |
| `api.py` | 仅标准库 `http.server`，只读端点 | 以上全部 |

**刻意的依赖方向**：`dim` 不依赖任何东西；`algebra` 只依赖 `dim`（纯数学，可独立测试）；`tree` 与 `search` 互不依赖。`api` 是唯一出口。

### 4.2 求值 `derivative` / `integral` 的接口设计

```python
def apply_derivative(f_dim: Dim, var_dim: Dim, order: int = 1) -> Dim
def apply_integral(f_dim: Dim, var_dim: Dim, order: int = 1) -> Dim
def apply_gradient(f_dim: Dim, var_dim: Dim) -> Dim
def apply_det(m_dim: Dim, matrix_size: int) -> Dim
```

**关键**：`matrix_size` 是**显式参数**，不从量纲推断（量纲里没有阶数信息）。这印证了 2.4 的建模原则，也说明为什么 `structure` 字段是必需的。

### 4.3 建树的来源优先级

```
输入名称
  → 别名归一 → 条目
  → 取 dim
  → ① 公式库反查：哪位公式的 lhs 或 rhs 项量纲等于 dim？
        收集其 relations，生成 equivalence / derivative / integral / matrix 边
  → ② 预置分解表：读条目 decompositions，生成 equivalence 边
  → ③ 有界搜索（仅"展开更多"触发，标注算法生成）
  → 渲染，同键异构并列成多卡片
```

### 4.4 最短路搜索的正确性边界

BFS 的完备性受限于剪枝规则。设计上必须明确：

- 剪枝规则（分母幂次 ≤ 3、原子数 ≤ 5、系数仅 1/2/3/4/60/3600）**会漏掉某些数学上合法的分解**
- 因此搜索结果必须标注为"有界搜索 **且** 算法生成"，而非"全部可能"
- 教学诚实性要求：搜到头就明确显示"没有更多有意义的分支了"，**不硬凑数量**

### 5.3 边的视觉区分（2.2 的落地）

| 边类型 | 视觉 | 口语化解释 |
|---|---|---|
| `equivalence` | 实线 | "同一个量的另一种写法" |
| `derivative` | 实线 + ⟨求导⟩ | "对 x 求导后量纲降低一阶，恰好是…的量纲" |
| `integral` | 实线 + ⟨积分⟩ | "对 t 积分后量纲增加一阶，得…的量纲" |
| `matrix` | 实线 + ⟨矩阵⟩ | "矩阵运算后的元素量纲" |
| 算法生成 | 灰色虚线 + 警示 | "算法枚举所得，暂未找到对应物理式子" |

### 5.4 "每一步都有中文名"的实现方式

每个节点携带两个字段：

- `display_zh`：中文写法（"焦耳每米"、"牛"）
- `display_sym`：符号式（`J/m`、`N`）

中文名**从注册表字段取得，不由符号反译**。这是硬要求：`J/m` 显示"焦耳每米"、`N` 显示"牛"，两者都在位，不需要翻译逻辑，也不会译错。

### 5.5 同键异构与结构标注

- 同一维度键下多个物理量条目 → 并列多张卡片，卡片头标注"⚠ 量纲相同但物理意义不同"
- `structure` 非 `scalar` 时在标题旁显示徽标（矩阵/向量/张量），并说明"元素量纲为…"

## 6. 测试策略

### 6.1 数据自检（最重要）

- 启动时对全部 `unit_forms`、`decompositions`、**`formulas.signature`** 做量纲一致性校验
- 测试：故意注入一条错误的 `dim`，断言启动报错
- 测试：故意构造一条量纲不齐次的公式签名，断言启动报错

### 6.2 代数规则单元测试（2.3 的落地）

逐条覆盖代数规则表，**特别包含**：

- `det`：2×2 矩阵每项 `[L]` → 断言 `[L]²`（最易错）
- `∫∫∫`：三重积分 → 断言量纲加 3 倍
- `gradient`：`dim(φ)=[M·L²·T⁻²]`，`dim(x)=[L]` → 断言 `[M·L·T⁻²]`
- `trace`：断言量纲不变
- `matmul`：断言量纲相加
- 边界：`derivative` 的 `order=2` → 断言减 2 倍

### 6.3 不变式测试

- 任意表达式的量纲 == 规范化到基本维度后的量纲
- 换算闭环 `A → SI → A` 回到原值（浮点容差内）
- **`derivative` 与 `integral` 互逆**：`integral(derivative(dim, x), x) == dim`

### 6.4 属性测试（property-based）

随机生成合法单位表达式，断言：

- 求值不抛异常
- 求得的量纲与逐项推导一致
- `parse → serialize → parse` 幂等

### 6.5 公式库齐次性

对公式库中**每一条**公式，按其 `ops` 推导 lhs 与 rhs 量纲，断言相等。这是公式库的自动化校对——比人工检查可靠，且新增公式时自动生效。

### 6.6 搜索正确性

- 对已知存在短分解的目标，断言 BFS 在限定层数内找到
- 断言结果按复杂度单调不减
- **断言剪枝边界**：构造被剪枝排除的合法分解，确认不被返回（测试固化已知取舍）

### 6.7 oracle 对拍

数值换算与 `pint` 交叉比对（仅线性单位；温度因偏移量特殊单独测）。`pint` 仅作**开发期测试依赖**，非运行时依赖。

## 7. 风险与开放问题

### 7.1 风险

| 风险 | 说明 | 应对 |
|---|---|---|
| 公式库是工作量主体 | 算法约 500 行，但公式库要持续添且需保证齐次 | 6.5 自动齐次性检查 |
| 手写 `dim` / `signature` 笔误 | 必然发生 | 3.7 启动自检 |
| 形状模式覆盖不全 | 匹配不上模式的公式要写显式规则 | 显式规则作为兜底，不强行归模式 |
| 矩阵阶数无处可推 | 量纲里没有阶数信息 | `structure` 字段 + 显式 `matrix_size` 参数 |
| 枚举噪声 | "展开更多"后段仍会出现无意义式 | 优先级过滤 + 灰色标注 + 允许"没有了" |
| 弧度建模 | 标记位是简化方案，不覆盖所有角度情形 | 先按简化方案做，留扩展字段 |

### 7.2 待确认的开放问题

1. **公式库首批范围**：力学/电磁学优先，还是全线铺开？建议先做力学（含求导/积分型），验证模式机制能跑通，再扩电磁学。
2. **变量未声明量纲时的行为**：报错要求声明，还是当自由未知量反推？后者教学效果更好，复杂度上升。
3. **公式是否渲染 TeX**：渲染需引 `KaTeX`，与"零第三方依赖"冲突。选项：纯文本 + 说明 / 引入 KaTeX / 自绘简单公式。
4. **非 SI 单位**（`bar`/`cal`/`psi`/`eV`）：教学场景是干扰项，工程场景需要。当前默认折叠。
5. **结构运算的展示深度**：矩阵/向量只标注结构，还是要显示行列数、对称性等具体信息？

## 8. 暂不纳入范围

- 数值单位换算计算器功能（本工具不是计算器）
- 复数单位、对数单位（dB、Np）
- 单位制之间的系统性转换（CGS/Gaussian 全套）
- **张量指标的升降与协变/逆变区分**（广义相对论场景；当前只做"矩阵/张量"的结构标注）
- 偏微分方程的完整符号求解（只做量纲推导，不解方程）
- 用户自定义单位与持久化
- 多用户、账号、部署

### 9.1 三项使用辅助功能（用户后续提出，已实现）

#### 9.1.1 搜索历史

需求：保留数量不低于 10 个，按时间排序，越靠近越优先。

实现选择：纯前端 `localStorage`（上限 50，去重后提到最前），零后端改动。
同时把查询词写入 URL hash（`#q=牛`），这样刷新、收藏、浏览器前进后退
与历史点击走同一条代码路径，不必引入路由库。

#### 9.1.2 公式补录（新增子系统）

需求：算法枚举出的组合若无现实物理式子，允许用户在条目处提交自己收集的版本；
核实为真则转正，核实不通过则标注存疑但**不移除用户改动**。

三条设计原则：

1. **用户数据与工具数据物理隔离**。提交写在 `dimensional-browser/submissions.json`，
   与 `data/*.json` 完全分开——重新生成数据文件不可能覆盖用户内容。
2. **只有 `verified` 进树**。`pending`/`disputed` 只在条目旁展示。理由：
   它们尚未被确认为现实物理式子，混进「依据现实式子」的树里会破坏该树的可信度。
3. **存疑不删除**。`disputed` 只加黄色标记，用户写的原文照常展示。
   核实结论与用户原文是两件事。

**核实机制尚未接入**，原因是拓扑限制：本地服务器进程没有联网能力，
`web_search` 属于 agent 会话的工具。所以设计成：`verify` 字段结构预留
（来源链接、判断依据、核实时间），`promote()` / `dispute()` 已实现并测试
（含非法状态转换拦截），接入核实时只需填状态、不动数据结构。

#### 9.1.3 公式符号表

需求：在物理公式处加折叠界面，包含公式中各个字母的名称与一句话物理意义，
点击可跳转到该量纲的页面。

**两跳解析**：先查 `data/symbol_glossary.json` 的例外表，再用 `(符号, 量纲)`
在物理量表里匹配。实测 84 组 (符号, 量纲) 里 26 组能被第二跳自动解决，
所以例外表只需写剩下的——且大多只要补更精确的中文名
（`E_k` 应为「动能」而非泛泛的「能量」）。

**按公式存，不全局存**：实测 `U`（势能/电势）、`L`（角动量/电感）、
`p`（动量/压强）、`I`（转动惯量/电流）四个符号同名不同义，全局表必然张冠李戴。
而「这句话里 m 是质量」本身就是最有价值的信息。

实现期踩到、并已写进测试的四个坑：

1. **符号表必须用 `(符号, 量纲)` 复合键**。初版用单键存储，
   自检立刻报「U 命中 2 种量纲」。
2. **跳转目标不能用字母序**。曾按 id 排序，导致 `E_k` 跳到「弯矩」
   （bending_moment 排在 energy 前面）。改为用公式库结构算「中心度」：
   某量作为越多公式的结果，就越是该量纲的主角。
3. **单位列必须是单位而非量纲**。曾显示 `L·T^-2`，应为 `m/s^2`；
   质量基准曾错成 `g`（克），因为 `g` 的符号比 `kg` 短就被选中了。
4. **需要给物理量补别名**。能量在公式里写作 `E_k`/`E_p`/`E_s`/`W`，
   力矩写作 `M`/`M_torque`。不认别名会让中心度打分全部为 0，
   进而退化成字母序——这才是坑 2 的真正根因。

### 10.2 实现中发现的、原设计未预见的问题

这些是真做起来才暴露的，记录下来对后续维护有价值：

1. **弧度伪维度与向量空间代数不兼容**（见 2.9）——设计阶段未想到的关键约束。
2. **建树时「关系属于哪条公式」需要按量纲校验变量一致性**。关系虽然写在
   公式对象里，但 `rel.wrt` 与该公式实际的求导变量可以不一致（`P = dW/dt`
   公式里写 `symbol='t'`，其 relations 却写 `wrt='s'`）；仅凭「公式有
   differentiator」放行会产生串味分支。这一处改到第五版才收敛。
3. **`Relation.from` 的匹配方向**：泛函关系里 `from` 是源量、`to` 是结果，
   所以建树要按 `to` 匹配才能找到「什么运算能得到这个量纲」。
4. **单字母变量与单位符号的歧义**（见 2.10）。
5. **多重积分的重数**：`∫∫∫ f dV` 里 `dV` 已含 `L³`，积分重数是 1 而非 3。
   写成 3 会让转动惯量的量纲算成 `M·L⁸`。
6. **搜索的代价上限必须高于最复杂导出单位的 L1 范数**。`Ω` 的量纲
   `M·L²·T⁻³·I⁻²` 的 L1 范数是 8，`max_weight=6` 会把它自己挡在门外——
   连唯一单位解都搜不到。改为 10。
7. **`g` 不能进搜索候选集**。它带词头（1 g = 0.001 kg），与 `kg` 同时
   参与会产生 `Pa·g/kg`、`Pa·kg/g` 这类「纯比例因子」组合：量纲正确、
   物理无意义。同理 `min`/`h`（accepted）与 `bar`（mixed）也只制造噪声，
   统一用 `max_unit_cost=2.0` 排除（代价编码了制式偏好）。

## 11. v4：用户报告七条问题后的修正

用户实际使用后报了七条问题。其中三条暴露的是**设计层面的遗漏**而不是实现缺陷，
值得单独记录。

### 11.1 去重键必须归一到「结构规范形」，不是「语法规范形」

原设计假定 `parse → render` 的结果可以作为表达式的唯一键。它**只保证语法幂等**，
不保证交换律归一：`N·m` 与 `m·N` 渲染成两个不同字符串。后果是同一个组合
在「常见写法」与「算法枚举」里各显示一遍。

修正：新增 `parser.canonical_expr()`，把表达式化归成**因子幂次多重集**的规范文本
（除法与负幂统一成指数、同名基指数相加、因子按基名排序、数字系数单独提出）。
它是比较键，不用于展示。同一个键也用于补录匹配。

**教训**：任何「这两个写法是不是同一个东西」的判断，都不能交给语法层。

### 11.2 泛函关系天然是双向的，原设计只建模了一个方向

原设计把 `derivative` 与 `integral` 当作两类**独立的边**，靠数据里各写一条来覆盖。
但求导与积分互为逆运算，**每条 derivative 都同时断言了一条 integral**：

```
F = -dU/dx   ⟹   U = -∫F dx      （微积分基本定理，量纲关系完全一样）
```

数据里 `derivative` 9 条而 `integral` 只有 3 条，看起来严重不对称；
真实原因不是数据缺失，是**建模漏了一维**。

修正：建树时对每条 `derivative` / `integral` 关系双向读一遍，掉头方向
（`kind` 互换，源改成 `rel.to`）也发一条边，带 `source.inverse` 标记。
判据严格——只有 `apply(源量纲, 掉头运算) == 目标量纲` 时才发。

这里的去重键是**边语义**（kind + 源表达式 + 变量 + 阶数）而非 `公式id`，
所以数据里显式声明的同一条边（冲量定理已经写了 `p = ∫F dt`）会与反读出来的
自动合并，显式那条优先。

**教训**：关系型数据里，「A 通过运算得到 B」这条陈述本身就是双向的；
把它拆成两条独立记录会制造一个永远对不齐的不对称。

### 11.3 页面需要一份槽位规范，否则结构会随数据完整度漂移

用户报告「不同量纲的页面内容实际并不统一（如有些量纲的常见写法下方有描述，
有些没有）」。根因是**没有规范**：每个槽位都写成「有数据就渲染、没数据整段消失」，
于是页面的**结构**成了数据完整度的函数，读者无法形成稳定的阅读预期。

修正：新增 [`2026-05-26-page-schema.md`](./2026-05-26-page-schema.md)，
规定固定的槽位清单、顺序与标题文案，并把空槽位分成两类：

- **不适用**：该槽位对本条目本就不该有内容 → 说明**为什么**
- **缺失**：应该有但没收录 → 「暂缺」+ 补录入口

「缺失」与「不适用」混为一谈是数据建模错误：前者要人去补，后者补了反而是错的
（给「长度」编一条定义式，写的必然是错的）。

为此在物理量条目上新增 `defined_as` 字段，取值 `si-base`（SI 基本量，
由基本单位定义）或 `umbrella`（总称量纲，如「能量」没有唯一定义式）。
**没有定义式的条目必须由这个字段解释清楚**，这条被写成测试。

同时把「常见写法」从裸字符串列表改成结构化行：**中文读法由求值器沿 AST 生成**
（`kg·m/s^2` → 「千克·米每二次方秒」），而不是写在数据里。这样它对每一条
都存在，「有些有描述有些没有」的问题从根上消失，剩下的只是可选的补充说明。

### 11.5 即时联想：不做全文检索，做「名称检索」

用户要求「直接在输入的同时匹配可能结果」，并指出「输入 a 可以匹配到 ab，
但 abc 不能匹配到 ab」——后者说明原匹配只做了单向前缀。

设计取舍：候选只有 84 个，摊平成 700 多个字段逐条打分只要 **1 ms**，
比建倒排索引便宜得多。匹配梯度按强度排序：完全相同 > 名称开头 > 名称包含 >
**反向包含**（输入更长）> 拼音全拼 > 拼音首字母 > 子序列 > 错字兜底。

三条刻意的约束（都是被噪声逼出来的）：

1. **反向包含要求候选至少 2 字符**——否则输入里含哪个字母就命中哪个符号，
   `abc` 会带出 `a`、`c`、`A`、`C`、`B` 一串
2. **错字兜底要求较短串也达到最短长度**——按较短串算重合率时，
   1 字符的符号与任何包含它的查询都得到 1.0
3. **弱字段（分类/领域）只认强匹配**——否则输入「电」会把整个电磁学分类翻出来

拼音用 `pypinyin` **在构建期**生成 `data/pinyin.json`（629 字），
运行时仍零第三方依赖。代价是新增中文条目时表不会自动更新，
所以 `selfcheck.py` 每次都核对一遍——漏字只影响那个字的拼音搜索，
因此算提示而非启动阻塞项。

### 11.6 导航：pushState 而不是 replaceState

原先只用 `replaceState` 写 hash——那是**故意**避开历史记录的写法，
于是后退键什么也退不回去。改成每次导航 `pushState` 一条，`popstate` 复原。

一个坑：**不能同时监听 `hashchange`**。`pushState` 改 hash 不触发它，
但浏览器后退会同时触发 `popstate` 与 `hashchange`，一次后退渲染两遍。

### 11.7 本轮修掉的实现级 bug

1. **反读对偶的前置比较写反了**：掉头后的边「源 = `rel.to`、结果 = `rel.from_`」，
   曾写成 `src_dim != dim` 就跳过——那是拿源的量纲跟结果的量纲比，
   一条对偶边都出不来。这个错误看起来完全合理，只有数一数「积分边还是 0 条」
   才发现。
2. **分母的幂次没生效**：`_derive_rhs_dim` 的 `div` 分支只累加 `dim` 不看 `exp`，
   `E_v = I_v/r²` 会少减一阶长度。数据里此前没有带幂次的分母，所以一直没暴露。
3. **同量纲异构槽位没有 `<section>` 外壳**：列表版本直接返回内容 div，
   导致该槽位在有数据时反而「消失」——正是 11.3 要修的那类问题，
   修的时候自己又犯了一次。
4. **匿名视图给了填不进去的补录入口**：未登记量纲的页面上，
   定义式/常见写法是挂在物理量条目上的，没有条目就无处可挂——
   应该显示「不适用」而不是给一个必然失败的补录按钮。
